# Security threat model

Scope: [canonical security policy](../security.md), [financial processing](../domains/financial.md), [AI boundary](../domains/ai.md). Assets are S3/S2 data, credentials, DEKs/KEKs, audit/projection integrity and availability. Boundaries are mobile OS/app, TLS ingress, trusted backend runtime, financial PostgreSQL/storage, independently permissioned KMS/lifecycle controls, telemetry and external AI. S1 metadata is confidential operational data but intentionally not encrypted everywhere.

| Threat | Protection provided | Residual risk | Required mitigation/evidence |
| --- | --- | --- | --- |
| Leaked PostgreSQL dump | S3/S2 encrypted payloads and authenticated wrapped DEKs; KEK unavailable in dump | S1 and approved S2 metadata, linkage/timing/lengths leak; stale ciphertext is retained by attacker | Dump inspection and key-separation tests; minimize selectors; no plaintext shadow/aggregate columns |
| Leaked backup/WAL/storage | Same application encryption plus infrastructure encryption | A wrap and corresponding KMS access together permit decryption; deleted users may remain in retained backup | Independent KMS roles, 30-day expiry, protected manifests and restore deletion filtering |
| Compromised DB read credentials | No S3 plaintext or usable raw keys in readable rows | Operational/S2-exception metadata exposed; queries may exhaust service resources | Private network, least-privilege roles, credential rotation and database audit without parameters |
| Compromised DB write credentials | AEAD rejects modified/transplanted payloads and binds meaningful metadata; external lifecycle cannot be reset by DB role | Deletion, replay, unanchored tail rollback, identity/role mapping corruption and denial of service; AEAD does not prove freshness or authorization | Owner constraints, trusted identity binding, least privilege, external ciphertext checkpoint anchors, restore/integrity alarms and PR-03 adversarial tests |
| Malicious/compromised application process | Per-user data keys limit exposure of one stolen DEK; no raw KEK in process | Process can obtain authorized users' plaintext/keys; its KMS workload permissions may unwrap many users | Patch/supply-chain controls, workload identity restrictions, bounded processing, egress controls, isolation and rapid credential/process quarantine; no claim encryption defeats this |
| Compromised production host | Storage encryption, no raw KEK and short-lived workload credentials | Host may impersonate app, scrape memory, use KMS and exfiltrate plaintext | Hardened hosts, least privilege, no debug shells/dumps, deployment controls, incident containment and full affected-key rotation |
| Compromised KMS credentials | Separate crypto/admin roles and context/purpose restrictions | Crypto role plus acquired wraps decrypts its authorized scope; administrator may deny/destroy keys | Short-lived workload identity, deny cross-environment use, two-person destructive control, KMS audit and incident drills; shared KEK does not give hard per-user IAM isolation |
| Insider access | Ordinary DB/support access lacks plaintext decrypt; access purpose and key operations audited | Privileged backend/KMS operator can access runtime data or bypass application deletion deny | Separation of duties, exceptional time-bounded approval, restricted production access and safe immutable security evidence |
| Stolen mobile device | Keychain/Keystore-protected refresh credential, no S3 disk cache, revocable sessions | Unlocked device/valid session can show data; root/app/OS compromise or external camera exposes plaintext | Remote revoke, short-lived sessions, background masking, device capability checks and logout/account-switch tests |
| Logs/telemetry leakage | Typed safe-event allowlist; no S3/S2/secret payload capture | Third-party auto-instrumentation can bypass application logger; opaque metadata still identifies activity | SDK/proxy/ORM/APM/crash configuration review and canary scans across normal/error/timeout paths |
| AI provider exposure | Deterministic minimization, no identity/raw history, strict no-retention/no-training contract | Bands/categories still infer private financial/career situation; malicious provider can see transmitted context; network metadata remains | Opt-in/disclosure, approved provider controls/subprocessors, no provider fallback, constrained egress and leakage evaluations |
| Cross-user authorization failure | Owner-first application checks, authenticated AAD/context, compound constraints and RLS defense | Backend resolving the wrong trusted owner can decrypt under its broad workload permission | Identity binding integrity, foreign-ID tests on every route/job/export, no client owner authority; encryption never substitutes for authorization |
| Prompt injection/model manipulation | No raw free text by default, no financial/game action tools, strict schemas and deterministic validation | Misleading advisory text or model inference remains possible | Injection/numeric/privacy evaluations, inert rendering, reject unsupported results, deterministic user-adoption commands |
| Key loss/KMS unavailable | Durable managed keys, independent lifecycle recovery, explicit fail-closed behavior | Lost last key is irreversible data loss; provider outage prevents necessary operations | Complete restore drills, dependency manifests, separated custodians and observable unavailable states without plaintext fallback |
| Rotation/migration failure | Versioned dual-read/single-write, fencing, bounded CAS migration, retained dependency keys | Interrupted migration retains old-key exposure; premature destruction loses backup/history access | Restart/concurrency drills, reference inventories, counters untouched by rewrap and restore proof before old key destruction |
| Nonce reuse/allocator rollback | Unique per-key sequence reserved outside financial transactions/restore boundary; old writers fenced | Lost/corrupt external allocator or unauthorized key use can defeat uniqueness | Never reset/reuse allocations, caps, trusted lifecycle head, unavailable-store fail-closed and restore concurrency tests |
| Replayed backup after deletion | Current external deny/tombstones survive DB restore; missing key registration denies use | Privileged KMS access plus archived wraps can recover data until dependencies expire; exfiltrated keys are outside control | No immediate crypto-shred claim, retention enforcement, isolated approved restores and final dependency destruction evidence |

Application-level encryption gives strong confidentiality against **database/storage-only** compromise, not against a trusted-runtime compromise. Encryption integrity does not prove complete audit history, prevent all traffic/metadata inference or provide availability. External ciphertext anchors narrow database replay risk only to their anchored cursor; the unanchored interval must remain explicit.

No design acceptance authorizes deployment with an unverified provider/control store. Residual risks belong in operational incident/privacy disclosures; do not replace them with marketing claims.
