# Security, privacy and cryptographic architecture

Canonical policy for PR-00.SEC. Implementation adapters/conventions and their production gates are owned by [persistence](persistence.md); Identity/session behavior is owned by [Identity](identity.md); executed evidence stays in [PR-02](prs/PR-02.md) and [PR-03](prs/PR-03.md). Detailed financial processing belongs to the [financial domain](domains/financial.md), model context to the [AI domain](domains/ai.md). [Threat model](security/threat-model.md) records guarantees/residual risks; [verification contract](security/verification.md) defines implementation evidence. Policy is finalized for downstream specifications; this is not evidence that an implementation or deployment has passed security verification.

## Trust and protection

The NestJS backend is trusted to temporarily decrypt authorized data for deterministic calculations, projections, reports, mission validation and minimized AI context. Application encryption protects S3 against compromise of PostgreSQL, its WAL/replicas/backups or storage alone. It cannot protect plaintext from a process/host that can execute authorized decryption. Do not claim E2EE, zero knowledge or operator inability to access runtime plaintext.

Use TLS 1.3 where available, minimum TLS 1.2 with secure managed configuration, certificate/hostname validation and no insecure mobile overrides, including backend-to-PostgreSQL/KMS/provider connections outside an isolated local development network. Production databases are private; no mobile/direct public database access. Encrypt infrastructure disks, database/WAL/backups and export/object storage as defense in depth. These controls do not replace application encryption.

## Classification and plaintext allowlist

S3 means highly sensitive data, not Amazon S3. Classification is by meaning and inference risk, not table name. New fields are S3 until classified in the implementing PR. Typed schemas separate approved metadata from encrypted payloads; arbitrary JSON/free text cannot be S1. SQL types, constraints and payload schemas must implement this map without introducing sensitive shadow columns.

| Field family | Class / persistence handling | Query rationale or restriction |
| --- | --- | --- |
| Amounts, balances, received/predicted income, spending, debts, interest/rates, receivables, reserve/goal amounts, required income | S3; encrypted payload | Never plaintext numeric columns, materialized SQL sums, amount indexes or hashes |
| Transaction/account labels, descriptions, merchant/payee/payer, bank/provider account numbers, source documents and attachments | S3; encrypted | No text search/index; external account identifiers never S1 |
| Goal names, allocation detail, forecast assumptions, report content, daily/monthly totals, financial evidence attached to missions | S3; encrypted | Projections/derived values inherit sensitivity |
| Employer, job title, salary, exact schedule, skills, career aspirations and private professional free text | S3; encrypted | Work profile reads authorized per user |
| AI context and results that contain/infer the above | S3; context runtime only, retained result encrypted | No plaintext prompt/output archive |
| Display/legal name, email, phone, address, birth date, profile biography and user-uploaded avatar references | S2; encrypted under the user's DEK | No local email/phone/name equality lookup, blind index or plaintext uniqueness requirement is approved |
| Opaque external authentication issuer/subject binding | S2 restricted exception; plaintext exact-match unique pair when required by PR-03 | Only issuer allowlist and non-email opaque subject; needed for identity lookup before user decryption; no provider profile/token payloads |
| Consents and purpose codes, policy version, granted/revoked time | S2 restricted metadata exception | Required enforcement/evidence; free-text explanations encrypted |
| Language, IANA timezone, non-financial UI preferences, catalogue avatar/cosmetic IDs | S2 restricted metadata exception | Necessary rendering/period interpretation; never career/financial values |
| Random internal user/entity/account IDs, ownership FKs, stream sequence/revision, request/job IDs, opaque idempotency key, correction/source-event references | S1; plaintext | Row lookup, tenant filtering, FKs, uniqueness and concurrency; client keys must be bounded random IDs, not descriptions |
| Created/updated/effective/due timestamps, report bucket boundaries, ISO currency, bounded technical state/event/rule identifiers | S1; plaintext minimum | Ordered/paginated period queries and validity constraints; merchant/location/free-text category and financially inferred eligibility/status remain S3 |
| Game XP/level/evidence or mission state derived from private finances/career | S3; encrypted | Plaintext cosmetic catalogue selection is not permission to reveal financial-health progression |
| Envelope header, opaque key refs/versions, lifecycle state, invocation counters, algorithm/schema versions, ciphertext and tag | S1 operational/ciphertext | Cryptographic routing/concurrency; not credentials and not financial values |
| Password, access/refresh token, API credential, signing key, KEK or plaintext DEK | Secret; dedicated controls below | Never ordinary profile metadata; no secret in logs, source or database plaintext |

S1/S2 exceptions expose linkage, timing, volume, currencies and selected operational states to a dump reader; they are still personal/operationally restricted, not public data. Timestamps may disclose schedules; only the indexed dates needed for the feature are allowed. Sensitive states (for example hardship/risk tier, reserve success or career eligibility) stay encrypted. Persisted technical metadata used in financial meaning is authenticated as described below. No global amount query or cross-user analytics exception exists.

PR-03 must use an approved trusted identity source/protocol with an opaque subject for the lookup exception. Authentication/session mechanisms remain its scope; a provider exposing email as subject does not satisfy this exception. Passwords, if introduced, require a separate reviewed credential specification; they cannot be encrypted with a user DEK and treated as reversible profile fields.

## Key hierarchy and custody

Production hierarchy: environment/purpose KEK in a managed KMS/HSM → wrapped unique per-user DEK version → encrypted user payloads. No DEK is reused across users or environments. KEKs are non-exportable to the application and reside outside PostgreSQL; production KEKs never appear in `.env`, images, source, CI variables or mobile. Workload identity with short-lived credentials grants only required wrap/unwrap operations; key administration, backup restore and destructive operations use separate privileged roles and two-person approval.

Use separate KEK namespaces for development, staging and production, and separate purpose keys for authentication/signing or infrastructure encryption. User data DEKs are not authentication/signing keys. Generate each DEK as exactly 32 CSPRNG bytes using the supported OS-backed runtime cryptographic API, never passwords, IDs, clocks, UUID bytes or application PRNGs. Wrap immediately; zero mutable buffers after use on a best-effort basis.

PostgreSQL key records contain only `user_id`, random `dek_id`, monotonically increasing per-user `dek_version`, `wrap_format=1`, immutable `kek_ref`/version, `provider_id`, opaque authenticated `wrapped_dek`, and bounded state/time metadata. Provider wrapping binds `environment_id`, `user_id`, `dek_id`, `dek_version` and purpose `forja.user-data`; a blob from another owner/environment must fail unwrap. Define binding as the fixed-order array `["forja-wrap",1,environment_id,user_id,dek_id,dek_version,"forja.user-data",kek_ref,kek_version]`, using the canonical JSON rules below. Managed adapters provide its equivalent authenticated context/AAD and return opaque native wrap bytes; the local adapter returns UTF-8 JSON `[1,"AES-256-GCM",base64_nonce,base64_ciphertext,base64_tag]`, with 32-byte DEK plaintext and the binding as AAD. A wrapper fingerprint is SHA-256 of the canonical JSON array `[wrap_format,provider_id,binding_array,base64_wrapped_dek]`. Enrollment/unwrap recompute this rather than trusting a DB digest. The result is an authenticated managed-provider envelope, not a homemade wrapping algorithm. The provider must support authenticated owner/purpose binding; [managed envelope guidance](https://docs.cloud.google.com/kms/docs/envelope-encryption) illustrates key separation, without selecting a vendor or adopting a per-record-DEK policy. Concrete KEK references never come from client input.

Platform exposes two narrow infrastructure contracts, no new service/domain module:

- `KeyProtectionProvider`: `wrap(32-byte DEK, trusted binding, approved KEK ref)`, `unwrap(wrapped envelope, expected binding)`, `rewrap(envelope, expected binding, approved target KEK ref)`, and provider health/capability checks. `rewrap` uses a native operation if supported or authorized unwrap/wrap within one short-lived process. The adapter output identifies its immutable provider/KEK version and authenticated wrapping format. Normalize failures; never return provider secrets/errors to clients. Provider adapters use established authenticated KMS primitives and test context rejection. Domain code sees encrypted storage/application values, not vendor APIs or key material.
- `KeyLifecycleStore`: strongly consistent conditional transitions, unique per-user versions, durable invocation-range reservation and key/deletion status, stored outside the financial PostgreSQL trust/restore boundary. It holds only opaque user/key refs, approved SHA-256 wrapper fingerprints/KEK refs, immutable identity-binding digests, counters, revisions and tombstones; no S3 or plaintext keys. Production uses an independently permissioned durable control store with backup/journal and restricted maintenance identity. It is justified by nonce uniqueness, rollback safety and deletion/revocation survival, not product caching; it is not Redis or a microservice.

KMS unwrap and encryption require a current lifecycle authorization check; unknown, deleted, revoked or invalidly bound keys fail closed. Neither store decrypts itself using a user DEK: workload identity accesses KMS and lifecycle controls independently, removing circular bootstrapping. Authenticated identity/authorization precedes key lookup. Provider choice and control-store implementation are PR-01/02 adapter/deployment choices only if these capabilities pass the verification contract.

Development uses a separate local-only provider: a 32-byte development KEK generated with the OS CSPRNG and protected in macOS Keychain, delivered into Docker through a private temporary mounted secret file, never committed or embedded in Compose/env text. Its authenticated wrapping uses the same AES-GCM policy with a distinct KEK invocation namespace in a separately persisted, atomic local lifecycle store. Developer keys and lifecycle files are outside the PostgreSQL volume; access is restricted to the developer. Loss makes development data unrecoverable; production refuses this adapter. Development is not a production key-management fallback. Test-only fixed keys/fixtures remain inside tests.

## User payload envelope and AAD

Approve AES-256-GCM with a 12-byte nonce and 16-byte tag through maintained runtime cryptographic libraries. No custom primitives, ECB, unauthenticated CBC, deterministic/searchable amount encryption or shortened tags. This is an established AEAD; the IV requirements are normative in [NIST SP 800-38D §8](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38d.pdf). Forja's limits and counter custody below are architectural choices, not a claim that this documentation is NIST-certified.

Persist envelope format 1 as a strict object with exactly: `format=1`, `algorithm="AES-256-GCM"`, `dek_id`, `dek_version`, `payload_schema` (positive integer), `nonce`, `ciphertext`, `tag`. Binary members use canonical padded standard Base64; no alternatives/duplicate JSON keys/extra fields. Nonce decodes to 12 bytes, tag to 16 bytes, ciphertext length equals plaintext length. No embedded KEK, plaintext DEK or client-supplied AAD is accepted. Buffer decrypted bytes without releasing/parsing them until full tag verification succeeds; clear/discard on failure. Encrypted payloads are UTF-8 JSON governed by a versioned typed schema; amounts use exact decimal strings/approved integer representation from the financial PR. Maximum plaintext per envelope is 1 MiB; larger artifacts are separate bounded chunks with authenticated chunk index and manifest. No sensitive compressed-length side channel is introduced by compressing mixed secret/user content.

AAD format 1 is the UTF-8 JSON encoding of a **fixed-order array**, without whitespace, using a single shared encoder and validated types:

`["forja",1,environment_id,user_id,entity_kind,entity_id,payload_slot,record_revision,metadata_schema,metadata_values,dek_id,dek_version,payload_schema,"AES-256-GCM"]`

UUIDs are canonical lowercase strings; kind/slot tokens are bounded ASCII catalogue values; positive versions/revisions are safe JSON integers; sequence numbers outside safe range are canonical unsigned decimal strings. `metadata_values` is a fixed-order typed array defined by `metadata_schema`, never an arbitrary object. For financial rows it binds the row's owning account ID, event/stream sequence, effective UTC timestamp, currency, technical state and correction/source link where applicable, including explicit nulls. Timestamps use UTC RFC3339 with millisecond precision. Other schemas list every meaningful plaintext field and its order in their PR. Bind report period/rule version, projection cursor and chunk index when relevant. Only the approved opaque S1 operational binding goes into AAD/provider context; no private content or direct identity does.

Construct expected owner/environment/entity/slot from the authenticated principal and repository contract, not a copied envelope header; verify tenant predicates before decryption. Envelope versions/schema/key refs are strictly checked against trusted configuration/lifecycle state. Authenticate all associated metadata before using it for a financial decision. Metadata mutation increments revision and requires new encryption/AAD. This prevents valid ciphertext transplantation across users/entities/fields; GCM alone does not detect rollback to a previously valid entire record. Transaction versions and external checkpoint comparison address the latter; the threat model states its limits.

### Nonces and usage limits

Every encryption invocation reserves a never-reused unsigned 64-bit sequence from `KeyLifecycleStore` for the specific immutable key ID. Nonce is four zero bytes followed by that sequence as unsigned 64-bit big-endian. All application instances share this allocator. Reservation commits independently **before** encryption; failed transactions, retries, abandoned batches and failed encryption burn their allocations. Allocations are bound to key/version and never used twice, returned or reconstructed from a financial row ID. No process-held reusable ranges survive process restart; each range has one owner and its unused suffix is discarded. The wrapping adapter's own AES-GCM keys use a separate identical allocation scope; managed KMS adapters own their native primitive's nonce contract.

New user DEK at 365 days or 2^31 reserved invocations, whichever first; hard cap 2^32 reserved invocations, then encryption fails closed until rotation. Maximum payload and cap also bound per-key data volume. Never reset counters, even on KEK rewrap. KEK-local development wrapping has the same caps and annual rotation. Known/suspected counter rollback or restored/cloned writers invalidate old encryption leases and force new DEKs before writes. Loss/unavailability of the allocator blocks encryption; random nonce fallback is forbidden.

## Lifecycle, rotation and recovery

Lifecycle transitions are conditional, durable and auditable: `pending → active → decrypt-only → retired`; `revoked` denies all ordinary use and `deleted` is terminal. At most one active DEK per user. Retired keys deny online use; recovery requires a separately approved isolated operation. Key creation writes wrapped material to PostgreSQL while pending, then activates only after verifying persistence and binding; interruptions leave pending keys unusable and are reconciled, not guessed. Operations register a per-user lifecycle admission/lease with trusted owner, purpose and lifecycle revision. Writers verify admission at the financial commit boundary. Rotation/revocation/deletion close admission and drain registered operations before completing their transition; a lease timeout is not proof a writer stopped. Hung operations require abort/confirmed termination of their runtime before the fence is released. Never switch keys or acknowledge revocation while an admitted writer could still commit. Reconcile dual-store interruption while keeping admission closed; availability yields to consistent fencing.

Unwrapped DEKs have **request/job-only lifetime**, no shared TTL cache, Redis, disk cache or reuse between requests. Reuse within one authorized bounded use case is allowed; release all references/clear mutable buffers in `finally`. Workers process bounded batches; the end of each batch releases keys and plaintext. Managed Node/C# memory cannot guarantee wiping strings, GC copies or library buffers. Disable core/heap dumps and memory profiling in sensitive runtimes, minimize copies and crash payloads, use infrastructure memory/swap protections and record this residual risk rather than promising perfect erasure.

| Operation | Executable procedure / completion condition |
| --- | --- |
| KEK rotation | Create an approved new managed KEK version/ref annually or on incident; make new wraps use it. Enumerate user-key records by cursor, rewrap each with identical owner/purpose binding, validate unwrap/32-byte result, install via CAS and enroll its canonical wrapper fingerprint in lifecycle metadata. During transition approved old/new wraps are readable; no payload re-encryption or counter reset. Keep old KEKs for retained backups; disable/destroy only when no live/retained wrap depends on them and a restore drill passes. Provider automatic KEK rotation alone is not proof all references migrated. |
| DEK rotation | Create pending new random DEK, persist wrap, fence/drain old writes, atomically designate new active version in lifecycle store; old version decrypt-only. New writes use new key. Migrate payloads in bounded per-user batches: authenticate/decrypt old, encrypt under fresh allocations/new key, CAS expected row revision/key and commit. Concurrent updates win; migration retries without posting new financial effects. Cursor/checkpoint persists only opaque progress. |
| Migration completion | Inventory every encrypted table/blob/outbox/artifact and all chunk manifests. Verify old-key live references are zero plus integrity/reconciliation checks before retirement. Maintain old wrapped keys/KEKs until backup expiration; do not delete them to make counts look complete. |
| Revocation | Mark key/user disabled in external lifecycle store, deny new key access, fence/drain in-flight operations, revoke sessions/jobs and clear references before acknowledgement. KMS-access revocation may require disabling workload credentials; per-user status is enforced by trusted backend, not magical per-user IAM isolation under a shared KEK. |
| DEK/KEK or host compromise | Quarantine runtime and credentials first; assess what was accessible. Rotate affected KEK and user DEKs and re-encrypt all retained live data as needed after restoring trust. Rewrapping an exposed DEK does not fix data confidentiality. Previously stolen plaintext/ciphertext with stolen keys cannot be made secret retroactively. |
| Failure/key loss | Unknown key, bad tag/context, KMS outage, unavailable lifecycle store or missing key dependency is an explicit unavailable/integrity failure; no zero balance, plaintext bypass, new key substituting for lost history or silent drop. Irrecoverable destruction of the last required key loses the corresponding data. |

KEK rewrap is a resumable dual-store operation: stage new wrap in PostgreSQL alongside old, enroll its fingerprint via lifecycle CAS, then switch the DB preferred ref. If interrupted, a registered old wrap continues to work; an unregistered new wrap does not. Never remove the old wrap before enrollment. Keep fingerprints for backup-dependent wraps until their backups expire. Here `kek_version` is the registered Forja wrapping-key epoch tied to its approved immutable resource ref. Record native material versions when the provider exposes them; otherwise its opaque authenticated wrap carries provider resolution metadata. Do not invent an unavailable native version or confuse either with the user DEK version.

Production takes daily encrypted backups plus continuous WAL/PITR, maximum 30-day retained backup window. Backups include wrapped-key records, encrypted payloads, envelope schemas and manifests of all DEK/KEK references. Lifecycle store/journal is independently protected/backed up; its authoritative head, tombstones and usage high-water marks are not rolled back with PostgreSQL. Keep managed KEK versions accessible for authorized recovery until the last dependent backup expires. No raw-key export or developer-held production key backup; use managed supported regional durability/recovery capabilities selected at deployment.

Restore in an isolated network with provider credentials limited to recovery; verify manifest/environment and current external lifecycle state first. Apply current deletions/revocations, reconcile financial projections/checkpoints, revoke restored sessions and jobs, and test decrypting non-deleted retained key versions. PostgreSQL rollback never rolls back nonce counters. Before enabling any restored writers, fence old deployments, mark all restored write-key versions decrypt-only and create fresh user DEKs lazily before each user's first write; old versions remain for authorized reads/migration. Before online access, complete an isolated recovery inventory of restored key references. Retired keys may be used only in isolated approved recovery: migrate their restored payloads into current active DEKs before ordinary access. Deleted users never re-enable; revoked versions require a separately authorized isolated incident migration, not automatic activation. No simultaneous writable production clone is allowed. If lifecycle high-water marks/tombstones cannot be recovered and trusted, restore remains closed; operator review cannot invent missing keys or silently ignore deletion. A restore drill before release and at least quarterly proves the complete dependency chain. Daily backup retention does not alone establish an RPO/RTO; select and demonstrate those targets before release.

## Authorization and authentication boundary

Authentication proves identity; authorization determines each read/write/export/AI/job's access. Encryption is not authorization. PR-03 must validate the trusted issuer, subject, audience, signature, expiry and replay/session rules; bind authenticated principals to immutable internal user IDs; define revocable sessions, least-privilege operator roles and step-up authentication for export/deletion/security changes. Never trust a mobile-supplied owner ID or database-editable role alone to grant decrypt permission. Credential/identity-binding integrity and compromised-write-DB attacks require explicit PR-03 tests.

PR-03 enrollment binds each internal user ID to `SHA-256(UTF-8 JSON(["forja-auth-binding",1,trusted_issuer,opaque_subject]))` in independently protected lifecycle metadata. Use the same fixed-array encoding rules; no email or private profile content. Only authenticated enrollment/approved identity-linking operations can establish/change this binding, with no financial DB role write authority. Before issuing a Forja session or unwrapping user data, compare the verified principal binding with that external record; an altered PostgreSQL subject-to-user mapping cannot alone grant access. Authenticated internal tokens must bind that verified user/principal; jobs use restricted system purposes, not fabricated end-user claims. This is the required identity integrity boundary, not a complete PR-03 login protocol.

Server-side persisted refresh/session bearer credentials are SHA-256 digests of independently generated CSPRNG tokens with at least 256 bits of entropy, never plaintext bearer tokens. Compare verifiers in constant time; rotate refresh credentials on use and reject replay. Access lifetime is at most 15 minutes and refresh absolute lifetime at most 30 days; PR-03 defines shorter limits, idle expiry and session UX. External per-user integration credentials, if later introduced, are encrypted as S3 under that owner; app-wide provider/API credentials and authentication signing keys live in independently managed secrets/KMS with separate purposes. Password login is not a baseline requirement and cannot be introduced without a reviewed credential-specific contract.

Server authorization and owner-filtered repository contracts precede unwrap. Use compound owner/entity constraints, transactional ownership validation and independent RLS as defense in depth where applicable, not as the sole authorization mechanism. Jobs carry an opaque owner and purpose; they recheck current authorization/revocation at execution. Background system permissions are bounded by purpose and do not give AI/support access to arbitrary users. No routine support plaintext browser; privileged access is exceptional, time-limited and audited with approved purpose.

## Safe observability and temporary processing

S3 and secrets never enter application logs, traces, metrics, APM payloads, exception reporting, analytics, queue metadata or diagnostic dumps. S2 is also excluded from telemetry; opaque S1 IDs are allowed only in restricted logs/audits, not high-cardinality metrics. Example schema: `event=financial.transaction.created`, `result=success`, `duration_ms=42`, random correlation ID, module and bounded error code. No body, amount, goal title, ciphertext/wrapped key/token, user name, bank ID, provider prompt/response or SQL parameter may be attached.

Implement typed allowlisted logging events; do not serialize arbitrary objects/errors/request bodies. Redaction is a defense behind the allowlist, not permission to collect raw data. Disable ORM parameter logging, SQL error payloads, HTTP middleware bodies, provider SDK debug, trace locals, APM/network captures and Unity crash attachments of runtime state. Normalize error codes before telemetry; sanitize untrusted strings to prevent log injection. KMS AAD/context may be logged by providers, so it contains only opaque operational binding. [AWS KMS documents this exposure](https://docs.aws.amazon.com/kms/latest/developerguide/encrypt_context.html); this is a capability requirement, not a vendor selection. The allowlist follows the risk guidance in [OWASP logging guidance](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html).

Requests return authorized plaintext over TLS with `Cache-Control: no-store`; reverse-proxy/CDN caches, persistent response caches and debug captures are disabled for sensitive routes. No plaintext S3 in Redis, temp files, swap dumps, CSV scratch space, queues or retry/dead-letter payloads. Outbox jobs store opaque references; any necessary sensitive job payload is encrypted with the owning user's DEK and authenticated job binding. Cross-user bundles are forbidden. Exports stream authenticated plaintext only to the authorized TLS response or use encrypted temporary user-owned artifacts; no public links or emailed attachments.

## Unity/mobile security contract

Baseline local persistence is limited to approved non-sensitive preferences, installation/session identifiers and catalogue assets. Financial/career/AI data stays in memory; no financial offline cache, screenshots saved by the app, PlayerPrefs payloads, SQLite files, plaintext HTTP cache or serialized scene state. Future S3 caching requires an ADR and bounded encrypted storage using an independent device-local key and per-user namespace/retention; it never uses or receives the server DEK.

Access tokens stay in memory. Refresh credentials use iOS Keychain `WhenUnlockedThisDeviceOnly`, no iCloud synchronization, and Android app-private token ciphertext encrypted by a non-exportable Android Keystore AES-GCM key with OS-managed nonce handling. Keystore stores keys, not arbitrary token strings. Require hardware-backed protection where available; inspect capabilities and document device support rather than silently claiming all devices have it. Disable token-file cloud backup/transfer. [Apple Keychain accessibility](https://developer.apple.com/documentation/security/ksecattraccessiblewhenunlockedthisdeviceonly) and [Android Keystore](https://developer.android.com/privacy-and-security/keystore) define these platform capabilities. Unity infrastructure uses reviewed native bridges; no secrets in C# assets/build configuration.

No background financial processing in the baseline; on background/lock clear sensitive views, tokens/plaintext references and cover OS switcher snapshots. Android secure-window flags block screenshots where supported; iOS obscures snapshots/capture where practical but cannot guarantee prevention of user screenshots or external cameras. Resume requires session validation before refetch; OS secure storage supplies refresh access only when unlocked. Logout clears credentials, sensitive memory, approved app-owned storage and pending work, and requests server session revocation. If offline, local logout is immediate and no revocation success is claimed; short-lived tokens and remote revoke/all-sessions controls bound device-loss risk. Reinstallation purges stale app Keychain session items before use; local account switching never reuses another user's namespace. Rooted/jailbroken devices and malicious app/OS processes can access displayed/runtime plaintext; secure storage does not solve this.

## Privacy, retention and deletion

Collect only purpose-bound fields; record processing purposes, lawful-basis review, consents where applicable, access/export/correction/deletion procedures and provider/subprocessor inventory with region/transfer review. AI processing needs clear disclosure and a separate opt-in; declining it does not disable deterministic Finance/Reporting. Terms of Use and Privacy Policy are separate pre-release legal deliverables. These engineering controls support, but do not constitute, LGPD compliance or legal text; see the [official LGPD text](https://www.planalto.gov.br/ccivil_03/_ato2015-2018/2018/lei/l13709.htm).

| Data | Engineering maximum/default |
| --- | --- |
| Active account financial/profile/goal/audit records | Kept for requested account functionality until authorized correction/deletion/account closure; annual purpose review, no unrelated analytics reuse |
| Regenerable report artifacts / retained AI results | 7 days / 30 days; user can delete earlier; only encrypted content, no persisted AI prompt/context in baseline |
| Temporary export artifact | At most 1 hour; authenticated owner access, cleanup on delivery/expiry |
| Sensitive job payload/outbox delivery artifact | At most 7 days after processing; unresolved failure quarantined encrypted for at most 14 days, alert/escalate and reconcile from authoritative records before removal; never silently lose financial events |
| Operational telemetry / security-access audit | 14 days / 90 days; safe metadata only |
| Database, storage, lifecycle backups/WAL | Maximum 30 days; deletion applies on every restore |
| External deletion tombstones | 90 days after the last dependent backup expires; absent key registration also denies old decrypt/restore |

A legally required exception must specify dataset, purpose, authority, expiry and restricted custodian before retaining it; no default indefinite legal hold. If a legally reviewed purpose needs longer retention, update this canonical policy through an ADR before production, not a hidden config override. Essential safety/deletion/audit metadata is minimized even when its security retention outlasts account closure.

Correction appends linked financial adjustments; account deletion is a separate authorized privacy lifecycle, not a financial correction. Ordinary immutable-history rules do not override approved erasure. Deletion first marks the user denied in the external lifecycle store, fences runtime work/revokes sessions, then purges live S3/S2 payloads, AI artifacts, exports, blobs, job payloads and all user wrapped keys; retain only minimal approved tombstones/security evidence. Retry/reconcile failures until confirmed. Legitimately retained data requires a separate restricted custody/purpose/key path and documented access, not continued ordinary-user access.

Deleting live wrapped DEKs alone is **not immediate crypto-shredding**: 30-day backups may contain recoverable wraps under retained shared KEKs, and privileged KMS credentials can bypass application tombstones. Restore filtering and denial protect ordinary access; irreversible user-data key destruction can be claimed only after all dependent wraps/backups/replicas/artifacts and any retained copies/keys expire or are verifiably destroyed. A shared KEK cannot be destroyed for one user while others depend on it. No claim is made that previously exfiltrated plaintext or keys can be deleted remotely.

Exports require step-up authorization and include the user's supported facts/provenance, not encryption keys or another user's data. Notify/security-audit export without payload logging. Incident response preserves safe evidence, isolates affected identities/hosts, assesses scope and invokes the controller/legal notification procedure. As of this review, [ANPD incident guidance](https://www.gov.br/anpd/pt-br/canais_atendimento/agente-de-tratamento/comunicado-de-incidente-de-seguranca-cis) describes a three-business-day notification rule for applicable incidents, with stated exceptions. The runbook must verify current applicability/deadlines with legal review, rather than treating encryption as an automatic reporting exemption.

## Implementation gate and deployment choices

PR-00.SEC defines policy sufficient for PR-01–04 specifications. Those PRs must implement and verify it; documentation readiness does not mean production readiness. Selecting a compliant KMS/control-store vendor, regions, OIDC/session implementation, exact library/editor versions and sizing is non-blocking for this design, but blocks the relevant adapter/deployment until demonstrated. Recovery objectives, legal retention exceptions and final notices require operational/legal sign-off before launch. No choice here changes the approved stack or product scope; the external lifecycle capability is a security infrastructure requirement justified by counter and revocation integrity.
