# RPG and game systems

## Boundary

Virtual progression never modifies real money. Character experience, levels, equipment and virtual rewards are game state, never financial assets or balance adjustments. Game has no Finance write capability.

Financial facts may qualify a mission or progression rule only through authorized server contracts. Mission completion does not prove that a real payment occurred. A user acknowledgement is not settlement evidence. Game consumes committed facts, never tentative client displays or model assertions.

The server owns persisted missions, completion and progression. Rule versions and triggering evidence identify why rewards were granted. Replayed evidence/retried requests must not grant duplicate rewards. Financial corrections require an explicit progression reconciliation policy before implementing rewards tied to that fact; never rewrite financial history to preserve a reward.

## Design baseline

The avatar represents the user. Character presentation may personalize appearance without inferring financial facts, gender or career from appearance. Offer male and female character directions under the [art baseline](../art-direction.md).

Mission mechanics translate financial-health goals into understandable actions. Present financial amounts and estimates using their financial labels; fantasy names cannot obscure obligations, debt, reserve targets or forecast status. Advice from Estrategista may propose a mission, but deterministic validated game commands establish its rules, evidence and reward.

No real-money reward, purchase, trading or monetization mechanic is approved by this foundation. PR-08 rule 1 below establishes the initial formulas/taxonomy/lifecycle under its explicit implementation request; later mechanics require a scoped product decision. Do not introduce engagement mechanics that punish financial hardship without explicit product review.

## Mission rule 1

Three small non-repeatable templates: GOAL_TARGET (GOAL_PROGRESS, 50 virtual XP), RESERVE_TARGET (RESERVE, 50 virtual XP), WORK_PROFILE (PLANNING, 20 virtual XP). Reserve is an explicit user choice on an owned dedicated financial goal; savings account type alone never infers a reserve. Goal/reserve variants share one source-goal assignment identity, preventing double rewards for the same goal. Work has one source identity per owner. No automatic assignment/claim or AI source; explicit candidate/assign/evaluate/cancel flow only. Fixed generic titles contain no copied goal name; objective/progress/evidence remain S3.

Goal eligibility: owned ACTIVE goal, active funding account, realized credited funds below its positive user-confirmed target. Capture target/currency/funding account, source revision and initial realized progress. Work eligibility: no confirmed Work profile yet; any subsequently validated Work profile qualifies, including zero availability/unemployment. No threshold infers financial health or punishes hardship. Start=server time, expiry=start+30×24 hours UTC; this is a mission window, not the financial goal deadline. At now≥expiry an ACTIVE mission expires before evaluation. No penalty for expiry/cancellation; terminal instance is not reassigned. Progress is current authoritative credited amount/target, or confirmed profile 0/1; no projection/receivable is a contribution. Goal evaluation requires unchanged target/currency/funding, ACTIVE or COMPLETED goal and active account; incompatible change/paused/cancelled source cancels an active mission rather than retargeting silently.

Completion and its XP award occur in the same admitted PostgreSQL transaction under the real user-row guard shared with Finance/Planning/Work. One immutable award per mission ID, serialized owner progression sequence and authenticated pointers prevent duplicate rewards. Evaluation time is the server database observation after acquiring the guard; committed completion records that qualifying observation before expiry. No process-local lock, full-database polling or implicit financial posting. GET reads never evaluate. Refresh/evaluate is an explicit retry-safe per-instance command; repeated unchanged evidence is a no-op. Assignment uses a UUIDv4 command/instance identity and unique owner/source; conflicting replay fails. Terminal missions retain original evidence and reward.

Correction policy: XP is a historical virtual acknowledgement, not certification of permanently retained money. Re-evaluating completed goal missions against changed configuration/account/credited funds appends a reconciliation marker and current source reference while preserving original completion/evidence/award. Never claw back XP automatically, reopen/reward again, or rewrite money/history. This marker records a changed basis, not a claim that every later expense is a reversal. New legitimate goals are independent sources; financial reversals cannot recycle an existing mission reward.

Progression curve 1: lifetime XP is the exact sum of immutable mission awards. Level=1+floor(XP/100); next-level threshold=100×level; remaining XP=threshold−XP. Integer safe bounds apply; XP has no price, transfer, monetary conversion or financial-calculation effect. First empty history legitimately reads XP=0/level=1 without a seed. No badge/cosmetic unlock or personalized tier/title is granted in this rule. Catalogue art/appearance is independent of XP. Future Estrategista uses the internal candidate/proposal validation contract only; no model-supplied fact, completion or XP can bypass deterministic assignment/evaluation.

All personalized mission state, type/category/status/reward/XP/progress/frozen financial evidence/reconciliation is S3. Plaintext selectors are only opaque owner/mission/source IDs, history/award sequences, revisions, timestamps and encryption routing. APIs omit internal evidence; mission revision/recorded timestamp show the last stored observation, not continuously refreshed Finance. History/read pages are bounded; status filtering occurs after decryption, with explicit continuation. Mission/XP inventories must participate in authorized erasure/recovery/key migration before deployment. Partial pointer replay/corruption fails closed; full valid Game history suffix rollback by a privileged DB writer remains a documented residual risk, not an external freshness guarantee.
