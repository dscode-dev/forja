# ADR 0021 — Grounded strategy and atomic Game adoption

Accepted within authorized PR-09.B local scope. Reuse PR-09.A provider, consent, shared cost receipts, owner serialization, synchronous admission and failure lifecycle. Its execution source was constrained to Chronicles; extend that source binding to actual encrypted strategy subjects with same-owner existence validation, preserving old ciphertext/AAD and Alquimista API. Never synthesize a financial report to satisfy its FK. Static purpose schemas/prompts extend the existing provider, not a second adapter/framework.

A strategy concerns a user-selected existing goal (GOAL or explicitly RESERVE) or GENERAL profile focus, never presumed global goal priority. No current recurring-expense declaration exists, so baseline/coverage/ideal target are UNKNOWN. Reserve purpose is a deliberate user interpretation of an exclusively funded goal, never inferred from savings-account type. Backend derives settled funding and last seven complete UTC-day movement, pending obligations/incoming, latest calculation compatibility, declared Work capacity and Game availability through public guarded reads. No arbitrary source text enters context.

Model selects reviewed finding/rationale and at most one catalogue template at version 1; backend renders inert restrained Portuguese. No invented parameters, urgency, financial targets, reward or executable logic. No actionable evidence or sparse context suppresses inference. All exact facts/version references remain backend-only/encrypted; provider sees allowlisted coarse codes/template IDs only. Current shared opt-in covers optional analysis/mission suggestions with updated disclosure, without new mandatory consent.

Strategies bind exact input fingerprints, source day, consent/prompt/config and Game catalogue version. Any relevant Finance cursor, selected-goal/calculation, Work or Game version change marks old strategy stale. Recheck inside the same existing Game assignment transaction; assignment plus encrypted adoption receipt commit together. Duplicate acceptance returns the original authenticated mission without reassignment, including after later source changes; a first stale adoption fails. Dismissal is an immutable owner decision. No model call can invoke adoption. No financial mutation or XP is granted by acceptance.

Provider and production gates from ADR 0020 remain unchanged; no external call is authorized. Broadening context/wording/templates or determining reserve coverage requires separately reviewed versioned rules.
